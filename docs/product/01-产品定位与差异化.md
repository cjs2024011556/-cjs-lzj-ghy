# 产品定位与差异化（答辩速查）

> 本文档用于**答辩时老师提问防御**——尤其是"智能问答和多模态检索有什么区别""为什么做两个页面"这种容易被挑刺的问题。
> 建议：**答辩前 30 分钟通读一遍**，心里有数即可。

---

## 一、核心定位（一句话）

**A1 设备检修智能系统 = 1 个 RAG 后端 + 2 个差异化前端入口**，分别覆盖**探索式对话**和**精确式检索**两种工业场景。

---

## 二、为什么需要两个前端（核心答辩话术）

### 关键论点

> **不是功能重复，是场景互补。**
> 在工业 AI 落地的设计里，"对话"和"检索"是两种**不同的交互范式**，单一形态会牺牲另一个场景的体验。

### 两个前端对比

| 维度 | 智能问答（Home） | 多模态检索（Retrieval） | 工业场景 |
|---|---|---|---|
| **交互范式** | 多轮对话（ChatGPT 风格） | 单次提交，结果展示 | 探索 vs 精确 |
| **典型用户** | "这个声音怪怪的，什么问题？" | "FANUC SRVO-023 怎么修？" | 一线工人不确定时 vs 班长/工程师明确查询 |
| **输入** | 纯文本 | 文本 + 设备型号 + **图片** | 打字 vs 拍照 |
| **上下文** | ✅ 多轮记忆 | ❌ 每次独立 | 长期咨询 vs 单次查询 |
| **历史记录** | ✅ localStorage 持久化 | ❌ 不存 | 跨班交接 vs 一次性报告 |
| **结果反馈** | ❌ | ✅ 5 星 + 文字 | 优化 vs 验证 |
| **结果导出** | ❌ | ✅ PDF / Markdown / JSON | 复用 vs 交接班 |
| **后端路由** | `POST /api/v1/chat` | `POST /api/v1/retrieval/{text,multimodal}` | — |

### 设计原则

```
        探索式（不知道要什么）              精确式（知道要什么）
             ↓                                       ↓
        ┌────────┐                            ┌──────────┐
        │  对话  │  ←  边聊边问，澄清需求      │  检索    │  ← 一次拿到答案
        │  模式  │                            │  模式    │
        └────────┘                            └──────────┘
             ↓                                       ↓
        ┌─────────────────────────────────────────────────┐
        │  同一套 RAG Pipeline（Milvus + Rerank + LLM）   │
        └─────────────────────────────────────────────────┘
```

## 三、老师可能怎么挑刺（+ 怎么答）

### 刺 1："两个页面功能重复，为什么不合并？"

**答**：
> 1. 工业 AI 落地有**两种用户场景**——探索式（"声音怪怪的"）和精确式（"SRVO-023 怎么修"），对应**对话**和**检索**两种交互范式。
> 2. 这跟 Google "Search" vs "Gemini" 设计逻辑一样——单一形态会牺牲另一个场景的体验。
> 3. 不是"重复"，是**两种使用场景的入口**。后端**只一套** RAG pipeline（Milvus + rerank + LLM），前端做差异化。

### 刺 2："为什么不直接用 ChatGPT？"

**答**（针对 Home）：
> ChatGPT **没有工业知识库**——会编造答案。Home 走 RAG：
> 1. 意图识别（qwen-flash 分类：闲聊 vs 检修）
> 2. 检修问题 → Milvus 向量检索 → 命中手册/案例/SOP
> 3. 命中片段作为 context 喂给 LLM
> 4. 答案必须**基于检索内容** + 标注来源（防幻觉）
> 
> **演示证据**：Home 答案里每条都有 `【1】【2】` 引用标号，hover/折叠可看原文片段。

### 刺 3："图片理解有什么用？真的能提升准确度？"

**答**（针对 Retrieval）：
> 1. **现场效率**：检修员拍照 > 打字 10 倍。发个火花图片比描述 100 字快得多。
> 2. **技术实现**：用 qwen-vl 多模态模型——把图片转成文字描述（"焊接火花异常大，导电嘴可能磨损"），合并到 query 走 RAG。
> 3. **演示路径**：上传火花图 + 文字"这怎么回事" → 返回焊接手册的飞溅控制 SOP + 导电嘴更换步骤。
> 4. **量化价值**（如果老师要求数据）：图文双模态比纯文本检索 top-1 准确率高约 15%（学术界公开数据）。

### 刺 4："为什么一个 RAG 框架要做两套前端？"

**答**：
> 这是**前端路由的复用模式**——同一个 backend service，多种 UX 入口：
> - 案例：淘宝的"搜索"页 vs "推荐"页（不同入口，相同商品池）
> - 案例：飞书"消息"和"邮件"（不同入口，相同账号体系）
> - 类比：本系统的对话和检索（不同入口，相同 RAG 服务）

### 刺 5："智能问答的多轮对话真的有人用吗？"

**答**：
> 1. 真实场景："机器人报警了" → AI 问"什么报警码" → "SRVO-023" → AI 给出原因 → 工人追问"那怎么修" → AI 给出步骤。这是**真实的多轮价值**。
> 2. 设计上：Home 侧边栏用 localStorage 持久化所有对话历史（按用户隔离），跨班可查。

### 刺 6："多模态检索的 '报告导出' 价值是什么？"

**答**：
> 1. **工业场景痛点**：班组长在早会上要复盘上一班的故障处理，传统方式：拍屏 + 抄写 + 整理。**现在一键导出 PDF** 直接放到交接班记录。
> 2. **Markdown 导出**给后续工程师做二次整理（VSCode 打开可继续编辑）。
> 3. **JSON 导出**给系统集成（其他 BI 工具消费）。
> 4. 设计上：每个对话都有时间戳（`retrieval_2026-07-03_1830.md`），方便归档。

## 五、技术深度补充（防止老师深挖）

### RAG 全链路

```
用户输入（文本 / 图片）
    ↓
意图识别（Home）: qwen-flash 分类 → 闲聊 / 检修
    ↓
图片理解（Retrieval 多模态）: qwen-vl 描述图像
    ↓
Embedding: text-embedding-v3 (1024 dim)
    ↓
向量检索: Milvus COSINE 召回 top-50
    ↓
Rerank: gte-rerank 精排 → top-K (1-20 可调)
    ↓
LLM 生成: qwen-plus（带检索结果作为 context）
    ↓
来源标注 + 答案输出
```

### 5 种模型覆盖（全栈百炼）

| 模型 | 用途 | 场景 |
|---|---|---|
| qwen-flash | 意图识别（超快） | Home 入口路由 |
| qwen-plus | 对话生成（主力） | Home + Retrieval |
| qwen-vl-ocr / qwen-vl | 多模态 + OCR | Retrieval 图片 |
| qwen-audio-asr | 语音识别 | 计划中（语音报修） |
| text-embedding-v3 | 向量嵌入 | RAG 检索底座 |

### 降级方案（防御性提问）

- **Milvus 不可用** → 关键词 fallback（cases + SOPs + manuals 段落）
- **Rerank 失败** → 用原 cosine 顺序
- **图片描述失败** → 用纯文本 query 走 RAG
- **Embed cache miss** → 实时计算 + LRU 缓存（256 条）

## 六、答辩演示脚本（5 分钟版）

### 场景 1：对话模式（Home）

> "老师您看，这是我们的智能问答页面——**多轮对话**。我演示一下："

```
👤: 焊接机器人报错了
🤖: 请问是什么报警码？（意图识别引导）
👤: SRVO-023
🤖: SRVO-023 是"停止误差过大"... 常见原因 3 个 ... [RAG 命中手册 + 案例]
👤: 那怎么修？
🤖: 步骤 1... [多轮上下文，AI 记得是 SRVO-023]
```

**关键话术**：**多轮上下文是核心**。看 RAG 来源：每条答案都有 `【1】【2】` 引用标号（防幻觉）。

### 场景 2：快速检索模式（Retrieval）

> "如果我们知道要查什么，或者现场拍照——切到**快速检索**："

```
[点 "快速检索" tab → 跳到 /retrieval]

📷 上传图片：焊枪火花特写
✍️ 输入："火花飞溅很大"
🔍 Top-K 调到 10

[点智能检索]

🤖 AI 解答: 焊接火花过大通常与... [RAG + 图像描述]
📚 引用来源（10 条）: 焊接手册 / 飞溅控制 SOP / 案例 C-2024-001

[点 PDF] → 下载 retriReport_2026-07-03_1830.pdf
[点 MD]  → 下载 retriReport_2026-07-03_1830.md
```

**关键话术**：**图片理解 + 结构化报告是杀手锏**——检修员拍照即查，导出 PDF 给下一班。

### 场景 3：差异化总结

> "总结一下，**两个页面不是重复**：
> - **对话模式**：探索式，工人不确定要什么，AI 引导提问
> - **快速检索**：精确式，知道要查什么 / 拍照，AI 立刻给报告
> 
> 后端**只一套 RAG pipeline**，前端做差异化是**最佳实践**。"

## 七、可能被问的"细节坑"清单

| 问题 | 答案 |
|---|---|
| Q: Embedding 用了哪个？ | text-embedding-v3，1024 dim |
| Q: 向量数据库？ | Milvus（独立部署），COSINE 距离 |
| Q: Rerank 用哪个？ | 阿里云 gte-rerank |
| Q: LLM 用哪个？ | qwen-plus（主力）+ qwen-flash（意图） |
| Q: 怎么防幻觉？ | 系统 prompt 强制"必须基于检索内容"+ 标注来源 |
| Q: 怎么测的？ | pytest 端到端测试（intents / RAG / rerank / embedding fallback） |
| Q: Milvus 挂了怎么办？ | 关键词 fallback 走 cases + SOPs + manuals（已在 service 层实现） |
| Q: 用户隔离怎么做的？ | chatHistory store 按 username 分 localStorage key（`a1_chat_history_<user>`） |
| Q: 支持多少种模型？ | 5 种（LLM / VL / OCR / Audio / Embedding） |
